# 插件与桌面端发布规范

[English](README.md) | 中文

## Summary

插件与桌面端共用源码仓库，但独立发版。版本标签对应单个产品的冻结源码；公开 Release 包含该产品已验证的可安装资产。开发里程碑保存在 Git 历史、PR 或 Actions artifact 中。[AFP 发布指南](../workspace/dsh-plugin-afp/release/README.zh.md)负责插件发布；[桌面端指南](../../apps/desktop/README.zh.md)负责打包、签名和生产上传。

## 产品版本族

| 产品 | 版本来源 | 标签 | 资产与更新选择 |
|---|---|---|---|
| AFP | AFP `package.json` | `afp-v<semver>` | `.tgz`、`SHA256SUMS`、`afp-update.json`；插件仅检查声明的稳定标签族 |
| 其他自定义插件 | 各自包清单 | `<plugin>-v<semver>` | 各自 tarball、校验和与元数据资产 |
| 桌面端 | 桌面构建版本 | `desktop-v<version>` | 已签名安装包、更新清单和匹配的更新产物；当前生产分发使用腾讯 COS |
| DSH npm 包 | 既有上游工作流 | `dsh-v<version>` | npm 包发布；该流程不发布桌面端安装包 |

AFP 与桌面端可以使用不同版本号和发布日期。只发布 AFP 不需要重建或发布 Windows；发布 Windows 时可以继续内置原来的 AFP 版本。用户所属应用先提供运行时更新器，之后才能独立更新 AFP。AFP Release 设置 `latest=false`，因为 GitHub 的仓库级 latest 无法同时代表多个产品族。桌面端 GitHub Release 负责分发记录，不代替当前签名的 COS 更新源。

## 发布步骤

1. 选择一个产品、新版本及已审核源码提交。核对该产品已有标签和 Releases；不得复用公开版本或移动标签。
2. 更新该产品的变更说明、双语指南和版本声明。运行相关测试及包检查；从待发布的干净、精确源码构建。
3. 准备草稿，写明产品名、版本、源码标签、用户可见变化、配置或数据迁移、重启要求、资产、支持平台与已知限制。公开前校验哈希和字节数。
4. 通过对应产品工作流发布。AFP 标签触发 AFP 工作流。桌面端执行签名、包验证和生产上传；既有上传器在生产上传成功后记录桌面端标签。桌面端 GitHub Release 仅在安装资产就绪且验证通过后公开。
5. 将公开资产下载到新目录复验。插件使用隔离 profile 做启动验证。保留冻结资产，通过新版本修正问题。

Release 标题使用 `AFP <version>` 或 `Desktop <version>`。正文仅描述该产品；共享源码改动只有影响其产物时才写入。代码里程碑不发布无资产 Release；GitHub 自动生成的源码压缩包不能替代插件包或安装包。预览构建使用 Actions artifact；明确对外分发的预览可以使用带真实资产、标记清晰的 prerelease，并使用独立更新频道。

## 里程碑与标签命名

正式分发使用产品标签 `afp-v<semver>`、`<plugin>-v<semver>` 或 `desktop-v<version>`。源码里程碑统一使用 `milestone/<subject>-<version-or-yyyymmdd>`，不创建 Release。只记录官方集成、视觉基线等需要长期引用的节点，普通功能修改由 Git 提交记录。

里程碑使用 annotated tag。附注写明节点用途、官方提交与实际软件包版本、本地源码提交、已实现功能及修复、保留的定制、当时实际执行的验证及失败或未验收项、后续集成与恢复用途。历史描述以原提交及原检查记录为依据，不补写后来才完成的功能或验证。修改附注前备份原 tag 对象，通过精确远端对象的 lease 更新，保持解析后的提交不变；正式产品标签与资产保持冻结。

| 保留标签 | 里程碑 |
|---|---|
| `afp-v0.1.0` | AFP 首个正式插件包，资产与源码保持冻结 |
| `milestone/upstream-v0.1.7-rc.2` | 早期官方集成与旧官方比较基点 |
| `milestone/settings-ui-20260928` | 设置页及 AutoFlow 视觉基线 |
| `milestone/upstream-v0.2.0-rc.1` | 官方 rc.1 集成 |
| `milestone/pre-upstream-v0.2.0-rc.2` | rc.2 集成前定制回退点 |

当前远程 Release 只保留正式 AFP 分发，源码草稿已删除。旧 `autoflow-*` 标签已按授权重整；非保留里程碑的提交仍属于 `main` 历史，精确原始标签对象保存在本机备份中。历史比较与回退命令使用上表标签；冻结 Agent Notes 保留原始记载。

## 更新验收

真实远程安装测试使用独立 `afp-test-v<semver>` 标签族、独立干净源码和隔离 `DSH_HOME`。仅测试检出将发布配置及安装所拥有的更新声明指向该族；正式 `afp-v` 更新来源保持不变。发布带实际三项资产的临时 Release，并设置 `latest=false`；同族稳定版本选择测试需要稳定标签，不能仅把测试 Release 标为 prerelease。手动安装与明确开启后的自动安装均检查重启生效、Host/Client/patch 来源一致、配置保留和失败恢复。

测试结束后删除临时 Release、Tag、profile、缓存、下载包和临时工作树，复查正式发行的资产摘要及远程引用。保留简洁的验收记录与历史标签备份。实际发布的测试包也必须来自已提交、干净、与 metadata 一致的源码。

## 恢复

重整前备份完整 Release JSON、精确 tag 对象、解析后的 commit、名称映射和可验证的 Git bundle。修改前重新读取远端，远端变化时停止，不能覆盖并发更新。删除旧引用后按映射重建同提交的重要标签，更新当前文档引用，并复验最终清单。正式产品标签重建必须恢复同一个对象，不移动版本或覆盖资产；发布修复仍使用新版本。

原始标签恢复使用保存的对象或 bundle；先检查远端是否已有同名引用，不覆盖新引用。远程删除是具体授权的治理或临时验收操作，日常更新无需删除既有标签。包降级需要明确支持的迁移，配置或数据变更可能阻止降级。
