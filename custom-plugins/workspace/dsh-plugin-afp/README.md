# dsh-plugin-afp

English | [中文](README.zh.md)

## Summary

An independent npm bundle for DSH profiles. Read tools, visual refresh, remote writes, six Skills and three workbench entry positions can be selected independently. Defaults enable all three Agent capability groups, all six Skills and the global panel; the settings entry and conversation tab start disabled. Remote writes still require a plan and explicit confirmation. All page positions show the same profile-owned tasks and reports. Closing a page or switching sessions does not stop a task.

## Install and develop

Run `pnpm install` at the repository root: AFP is a workspace dependency of the CLI. New Web/Desktop profiles select it automatically; Headless and SDK profiles do not. `pnpm run build` rebuilds its browser entry, and Desktop packaging includes its tarball. AFP keeps its own package version without declaring an exact DSH peer version. Existing profile bundle selections are preserved; see the [upgrade guide](../../../docs/upgrade-guide/v0.2.0-rc.2/afp-builtin/guide.md) for replacing a profile-local installation.

Run `pnpm --filter dsh-plugin-afp test` and `pnpm --filter dsh-plugin-afp check` from the root. Use `pnpm --filter dsh-plugin-afp pack` for a reviewed standalone artifact. Repository updates followed by `pnpm install` and `pnpm run build` update the builtin package; restart the Host when module watching is disabled. The package defines no application bin. Source attribution and publication limitations are in [UPSTREAM.md](UPSTREAM.md).

GitHub distribution uses the package's `afp-v<version>` tag and an independent tarball, checksum and version metadata; see [publishing AFP releases](release/README.md). Plugin details check stable versions automatically. Enable automatic download/installation or choose Update now; restart applies the new version while retaining feature choices and configuration. The running carrier must already include the updater.

## Directory reference

Root `index.js`, `execute.js`, `skill.js` and generated `client.js` are exported lifecycle entries. `config-schema.js` validates deployment settings. Host implementations live under `src/host/afp-*.js`; browser implementations live under `src/client/afp-*.js`; adapted protocol and category policy modules live under `src/vendor/auto-afp-img/`. `skills/` contains instructions and references only. Root `cli/afp-task.js` exports a DSH-managed task adapter calling the same Host service as the UI; `scripts/` contains package build/check scripts. Edit browser source and run `npm run build:client`, rather than editing generated client.js.

## Icon assets

`assets/icons/` contains the AFP logo and twelve feature SVGs. The manifest declares their file paths; Plugin Manager serves them as file URLs without Base64 in Web. Feature icons use CSS masks with the page's semantic color tokens, including dark themes. Missing images fall back to the feature category artwork.

## Configuration

Download destinations support both the native Host chooser and the Web browse backend. The browse dialog lists existing Host directories, supports absolute-path navigation, and binds the confirmed directory to an expiring Host-only ID. Download plans cannot supply paths directly; native deployments reject browser-supplied paths. Neither picker mode creates directories or AFP relationships.

Configuration editors reserve their loaded form height and show matching skeleton fields during the first read. Visual refresh uses account/authentication and model/budget columns on wide windows and one column below 760px. Fields sit directly on the dialog surface, grouped by headings and spacing. Content scrolls inside the editor; Save stays visible, including when Advanced expands. Read failures preserve the editor size and show an alert.

In the workbench's Visual model section, model settings and screening parameters share the left card with Save; Advanced configuration occupies the right card and starts expanded. Both cards use the AFP account layout's column proportions and matching heights, stacking below a container width of 860px. The JSON editor fills the right card and shares one draft and save action with the model fields; collapsing it or switching sections retains unsaved edits.

The packaged `config.json` is an initial template. The authoritative user file is `<profile>/.plugins/dsh-plugin-afp/config.json`, containing `version: 1` and a complete boolean `features` map. Plugin-page changes and manual edits use this same file. HMR watches it; profiles without HMR require a restart. Invalid files remain unchanged and produce an error; the last running configuration remains in place during a failed HMR read. A managed save that fails during activation restores the previous file and running choices. Explicit legacy row selections migrate on creation; subsequent startup and upgrades retain the user file. Renaming/removing feature IDs or changing file versions requires an explicit migration rather than overwriting selections.

Feature keys are `read`, `refresh`, `write`, `ui-settings`, `ui-panel`, `ui-conversation` and the six Skill directory names. The plugin page and workbench distinguish selected state from actual running state. Home/command-line deployment overlays remain higher priority. The root bundle toggle retains all choices. Managed Skill instruction upgrades accept only known packaged revisions or an unchanged installed digest; customized instructions remain intact. Removing one UI entry only removes that entry; disabling refresh/write cancels and drains corresponding jobs. There is no prompt-injection feature in AFP. The root requires credentials, jobs, profileContext, pluginManager, configEditor, directoryPicker, sessions and sessionQuery through a Cordis service-name array. If the root stays pending, its tool and Skill rows cannot activate; a plugin mention alone does not make AFP tools available.

Credentials are resolved through the DSH credential service using `AFP_ACCESS_TOKEN` or `AFP_USERNAME` + `AFP_PASSWORD`, and `VISION_API_KEY`. Only reference names are configurable here, never credential values. Token cache remains in the credential provider. The configuration dialog enables Get token only after both AFP username and password are entered; it saves them, then reuses the runtime login flow to acquire or refresh the token. The button shows its spinner while the request runs, and acquisition does not return the token or write it to plugin JSON. An explicit eye-button action can reveal the saved credential. Set `visionBaseUrl` and `visionModel` on Cordis row `afp`; see [config.example.patch.yml](config.example.patch.yml). Endpoints, model settings, timeouts, limits and `pollIntervalMs` are deployment fields, not feature JSON. The legacy deployment `allowWrites` field is accepted for stored-run compatibility and no longer grants permission; the `write` feature row controls writes. Token-only account identity changes when its token changes; username-based accounts keep stable identity.

Credential inputs use a visual mask and disable browser autofill; DSH owns their saved values, and the eye button still reveals or hides each field independently. The workbench account card fills its grid column, with a 16px gap before Account information; below a container width of 860px the cards stack.

In a report, left-click a thumbnail or title to review the large preview. Right-click or choose Photo details to open metadata. Review displays the original decision, confidence and reason; only passed images can be added to the shared selection, while selected images can be removed. The selection list and Add to favorites entry reuse the existing snapshot confirmation dialog and permission checks. The favorites dialog uses a more opaque glass surface and stronger blur, with separate selection, scrollable target-list and footer regions; its material overrides remain local to this dialog. Browsing or selecting images does not change automatic decisions, rerun vision requests or write to remote collections.

Every AFP visual run retains stage timings and sanitized failure diagnostics independently of terminal logging. Collection directory reads, membership reads, parsing, search initialization, checkpoint saves, preview downloads, vision reviews, confirmations and progress callbacks are timed separately; concurrent and nested durations cannot be added to calculate total time. Expand Run diagnostics in a Tasks report and choose Export diagnostic log to download JSONL. The first line contains the summary and subsequent lines contain detailed events. Older runs explicitly report unavailable diagnostics rather than reconstructing historical stacks. Status polling refreshes the photo report when its review summary changes; diagnostic metadata alone does not clear the report, close its image preview or collapse its diagnostics panel.

Run reports expose `diagnostics.durationMs` for the current refresh attempt, with `durationScope=refresh-attempt`, sanitized failure locations and timing summaries; tool `meta.durationMs` measures that report read only. A blocked preview retains `preview-host-blocked` and the hostname without its signed URL. After saving outcomes for admitted workers, the batch stops admitting additional previews. Verify the hostname before adding its exact value to `previewCdnHosts`; empty configuration does not permit arbitrary CDN redirects. Exhausted checkpoint writes report `checkpoint-save-failed` separately from preview failures.

Record replacement supports Windows and macOS, including Unicode paths and spaces. Both retry transient `EBUSY` and `EINTR`; Windows also retries short-lived `EPERM` and `EACCES` sharing failures. macOS permission failures stop immediately. `stateWriteRetryCount` defaults to 8 (0 disables retries, maximum 20); `stateWriteRetryDelayMs` defaults to 50 (10..1000). Retries apply only to the same temporary-file rename, not AFP requests or completed visual judgments. Persistent failures stop after this budget and retain the previous file. macOS system directory aliases `/var` and `/tmp` are accepted only when resolving to `/private/var` and `/private/tmp`; profile-owned directory links remain rejected.

The AFP release workflow requires native Linux, Windows, Apple Silicon macOS and Intel macOS package checks and tests before publication. Native jobs build Host dependencies before testing the real Cordis job registry. Windows file-sharing tests run on Windows; open-reader replacement and private-file permissions run according to the current platform. Simulated macOS errors in a Windows test run verify retry policy only and do not establish native macOS execution.

The advanced account configuration provides Enable detailed Debug diagnostics. Saving reloads AFP, so wait for current tasks to finish first. Newly started or resumed tasks use the current configuration; resuming replaces that run's previous diagnostic window. `debugEnabled` defaults to false. When enabled, it additionally records operation start, end and failure events. When disabled, failure codes, allowlisted local error names and filesystem codes, up to five sanitized code locations, and timing summaries remain available.

Diagnostic files live under the profile's private `diagnostics/<runId>.json` storage and correlate tasks through `runId`, `attemptId` and `jobId`. Defaults are `debugMaxBytes=262144`, `debugMaxEvents=1000`, `debugMaxRuns=20`, `debugRetentionDays=7` and `debugFlushIntervalMs=1000`. Events exceeding capacity are omitted and counted; completed runs prune older diagnostics by count and age. Diagnostic write failure never replaces a business exception; the same service retains bounded in-memory records for export. Exports exclude credentials, account contents, candidate photo identifiers, media URLs, request bodies and response bodies. Authenticated reads require an existing run in the current profile; detailed events are not automatically added to model context.

Browser tests capture page errors and request status, then correlate backend diagnostics by `runId`. `node --test tests/diagnostics.test.js` covers silent logging, progress callback failure, checkpoint write failure, capacity and retention, profile isolation, sanitized exports and settlement through the real Cordis job registry. Simulated API tests do not establish successful real AFP or vision-provider execution.

## Conversation search and final results

Ordinary photo search does not enumerate fixed category collections or start visual curation. AFP owns full safe photo metadata under the profile's conversation-results directory, scoped to Session, Turn and successful call identity. Records contain no credential values, signed media addresses or image bytes. Native results persist presentation metadata; nested calls recover the complete record through resultRef and the authenticated conversation-result operation. Reads from another Turn, failed dispatches or foreign calls are rejected. Existing failed sessions are not repaired.

The model receives valid JSON bounded by agentResultMaxBytes (default 16384, range 4096–65536). afp_result_page reads remaining local metadata without AFP requests. New search, details, collection-member and final-selection records are independent of general output truncation. afp_photo_selection requires basis=metadata with runId=null, or basis=visual with a real run report read successfully in the same Turn. afp_report accepts kind=run|plan and id. afp_refresh starts with mode=start, categories and runId=null, or resumes with mode=resume, categories=[] and a real runId. Collection write approval remains unchanged.

AFP does not register a separate progress capsule above the composer. The native checklist shows task planning, while search and visual-review progress remain in inline conversation disclosures; the workbench and download progress entry remain available.

One collapsible candidate gallery belongs to the process and collapses after completion. Only a successful explicit selection creates the final gallery and structured table, preserving selection order and showing description, AFP photo ID and a same-origin authenticated preview link without login tokens. Metadata results state that no visual review occurred; visual acceptance comes from the saved report. Reload reads persisted metadata rather than reconstructing a selection from assistant text. The Agent uses three short paragraphs for outcome/count, criteria/basis, and unmet requirements or errors; failed selection cannot be substituted with a handwritten list or shortened IDs. The interface owns the fixed gallery/table layout and shows saved criteria.

## Content and recovery

### Automatic AFP authentication recovery

Hub may wrap a rejected refresh as GraphQL HTTP 200 with the exact message `Request failed with status code 401`. Host classifies that response only for `refreshToken` as authentication failure, allowing one login fallback. Wrapped 403, service, schema and unknown errors do not enable this fallback. Configuration acquisition returns `acquired: false` with a fixed safe error category on failure; the editor distinguishes authentication, permission and transient service failures without returning upstream text or claiming success.

The deployment field `autoRefreshToken` defaults to `true` and can be disabled in Advanced settings JSON. Host verifies image access using a minimal FAR `getPhotos` metadata query; an SLT collection HTTP 200 does not establish image authentication. JWTs renew within `tokenRefreshMarginSeconds`. Opaque tokens have no decoded expiration and are verified when opening a connection. Explicit HTTP 401 and fixed GraphQL authentication categories initiate recovery. FAR also rejects stale grants as GraphQL FORBIDDEN: only the cached-token probe permits one renewal for that response, and the new grant must pass FAR validation before storage. Business permission failures, fresh-grant denials, HTTP 403, query, schema, unknown and rate-limit failures do not start recovery loops. A static token without username/password or a refresh grant cannot renew itself.

Access and refresh grants from login stay in DSH credentials. Host first uses the website's Hub `refreshToken` mutation and falls back to login only when refresh is explicitly rejected and username/password are configured. Legacy access-only caches acquire refresh credentials on the first rejected authentication. Auth mutations have no automatic transport retry, and the new access token must pass FAR verification before storage. Per-account credential updates are serialized with a generation counter, preventing parallel renewals even when access-token values stay unchanged.

A read that loses authentication after opening may renew once and replay the original read once; a second rejection fails directly. Purchases, delivery downloads and collection mutations are never replayed by authentication recovery. Cancellation prevents grant commits and read replay. Tools, Sessions, run files and ordinary configuration metadata never include refresh credentials. Agent errors distinguish authentication, authorization, query rejection and `upstream-error`; an unknown GraphQL error does not establish invalid search parameters. `verifiedAt` records the last FAR validation, not an upstream expiration claim.

The account section reads the Hub `user` query through the Host and displays identity, email, user/client IDs and `credit.amount` beside the credential form. Zero credit is displayed as zero; absent credit remains unavailable. Account loading and retry do not block credential editing. No administrator, purchase or download-history operation is called. Stored passwords and keys remain in the credential provider.

The collection sidebar lists named collections as compact project Button rows with folder icons, document counts and a shared hover/focus highlight. Read-only or shared permissions appear as Tags; writable private rows omit the repeated permission label. Initial selection skips unnamed entries. Its collapse control sits beside the filter; folding retains actionable collection initials with full-name, permission and count tooltips. Wide layouts retain a 56px rail; narrow layouts use a horizontal strip. Width and text transitions follow the Models rail and respect reduced motion. Filtering, the current collection and photo selection survive folding. Photo selection uses a compact frosted-glass rounded-square indicator with a translucent fill, local backdrop blur, a white SVG check and a matching photo-frame outline inside a project Button with a pressed state; it appears on selected images and on hover or keyboard focus, and never opens details. Gallery cards use equal 4:3 preview frames for loading, success and failure; thumbnails fill the frame with proportional cropping, while details and large previews retain the complete composition. The selection drawer closes through the selection summary toggle and omits a duplicate header close button. On wide screens it fills the gallery height, with its heading and clear action fixed around an independently scrolling list; narrow screens retain a bounded stacked drawer. Row removal controls appear on hover or keyboard focus and stay visible on touch devices. Action tooltips use short localized labels with a capped width; full photo titles remain in accessible button names. Folding the drawer preserves selected photos. AFP choice menus measure their actual trigger and scroll within a bounded card; collection-operation dialogs use a compact, readable surface. The selection summary combines up to three complete thumbnails, overflow and a count Tag into one drawer button; batch actions remain separate. The AFP Settings section hides the shell action footer to give the workbench more height. The photo browser excludes explicit non-photo `docClass` entries while retaining legacy entries without that field; write validation still checks every member. Gallery and details scroll independently, and Back to top appears after half a visible gallery height. Skeletons and image fades respect reduced motion. Clicking a detail preview opens the project Modal with focus restoration. Preview consumers hold shared raster Blob URL leases; the last consumer release revokes the URL. The Host negotiates JPEG/PNG/WebP/GIF, accepts matching raster signatures with generic binary MIME, and rejects HTML/SVG. Blocked CDN errors report only a hostname; verify that domain before adding it to deployment `previewCdnHosts`. Signed media URLs and AFP credentials never reach browser metadata.

## Preview cache

Previews use a minimal skeleton while waiting, fetching or decoding: a flat background fills the image area, with a low-contrast diagonal highlight sweeping slowly across it. Titles and actions stay visible. The animation uses CSS transform, without Three.js, Canvas, WebGL or a JavaScript frame loop. Offscreen, inert or hidden-page previews pause; the skeleton disappears after the image load event, and failures retain Retry. Reduced motion shows a static background; the deployment setting `previewAnimationEnabled` (true by default) disables the sweep. The localized loading status remains accessible without fabricated progress or extra spinner text. Unmounting disconnects intersection observation and page-visibility listeners.

Preview recovery uses deployment settings `previewRetryCount` (default 2; 0 disables recovery; maximum 3) and `previewRetryDelayMs` (default 1000 ms; range 100..30000). Transient transport, timeout, rate-limit and service failures re-fetch only the current preview with exponential delay; fetch and decode failures share one per-preview budget. Recovery pauses when offscreen or the page is hidden and is cancelled on unmount, photo, permission or credential-scope changes. Exhaustion shows a compact error placeholder and Reload preview; manual reload starts a new budget and invalidates that preview cache entry. Authentication, blocked CDN, unsupported raster and unknown proxy errors do not automatically retry. The proxy returns only a safe retryable flag, not provider diagnostics. Concurrent consumers continue sharing preview requests and successful cache entries. Older Hosts without the policy retain manual reload; installing these Host changes requires restarting the app. Preview recovery never replays a search, purchase, download or collection write.

The plugin store owns a page-memory cache shared by gallery, detail, selection and download previews. Concurrent consumers share one request; successful raster Blobs use LRU retention. Deployment JSON sets `previewCacheMaxEntries` (default 300; 0 disables retention), `previewCacheMaxBytes` (64 MiB), and `previewCacheTtlMs` (10 minutes). Expiration is checked on acquisition, release and cache inspection. Entry/byte limits cover retained Blobs, excluding active images, DOM and decoded memory. A closing consumer cancels only its subscription; the last waiting consumer aborts the request, and the last URL lease revokes its object URL. Failed requests are not retained; decoding failures and explicit retries invalidate the matching version. Credential, read-access, connection and Host-scope changes clear previews and suppress late completions. Disposal drains owned reads. Browser refresh clears memory; no persistent files, signed media URLs, credentials, paid originals or quotes are cached. Host HTTP responses remain authenticated and `no-store`.

`node scripts/benchmark-preview-cache.mjs` compares six uncached and cached consumers with an offline 40 ms transport. It asserts request counts, not browser rendering speed.

## Visual execution budgets

New afp_refresh starts accept targetPerCategory (1–1000) and minimumReviewedPerCategory (0–1000). A request for 10 accepted photos should pass targetPerCategory=10; the optional minimum is an independent completed-pixel-review requirement. Resumes omit both fields and retain saved settings. The first review batch is bounded by batchSize and the remaining accepted/minimum-review deficit; quality gates, aesthetic score 5 for landscape and its second confirmation pass remain unchanged.

Search uses searchConcurrency (default 3), maxPages per query variant (3), and maxSearchRequests logical page calls per category per start (30). New batches do not renew either page or request budgets; a new resume continues saved cursors and queued candidates with a fresh search budget. Every completed page saves its cursor and pending metadata together, including successful pages when a peer source fails. Only schema/query rejections permit structured-field fallback; authentication, authorization, cancellation, timeout and rate limits do not. Reports include safe search counts and fixed failure code/stage/retryability; they never expose provider bodies or signed media references.

The supplied API client owns retries; search strategy never wraps it in another retry loop. Transport and response-body reads share one readRetries budget per logical read (default 2 retries, at most 3 attempts). Preview metadata and image delivery use separate bounded reads, so a delivery retry does not reread metadata. Interrupted workers drain before the run lock is released; completed images are not replayed, and parallel completion order does not change the retained quota.
