## 集成决策规则

1. **功能新增：**原则上保留 AutoFlow 能力，包括状态、持久化、文案、无障碍与测试。若官方修改了同一接口或流程，应将功能适配到新的官方实现，不能整文件覆盖任一方。
2. **纯视觉改动：**默认保留本次样式基线。先对照官方与 AutoFlow 的亮暗模式效果；若拟用官方样式覆盖本地颜色、间距、几何形状、动效或布局，列出具体组件、差异和影响，并在改动前征求用户明确确认。未获确认时不覆盖。
3. **功能附带的样式：**官方新功能所必需的新增样式随功能合入，并与本地主题适配。若适配会替换现有样式，先按上一条取得确认；仅补充新功能所需的样式无需覆盖旧视觉。
4. **混合文件：**按代码块审查。功能逻辑可适配官方变化；同一 TSX/CSS 文件中的本地视觉仍遵守先确认后覆盖的规则，不对整文件使用“全部保留本地”或“全部采用官方”策略。
5. **生成及辅助文件：**选定代码后重新生成或更新相关快照、翻译记录、锁文件和文档。旧快照不能代替真实产品行为。

每个区域在下次集成时记录旧/新官方提交、涉及路径、选定的功能行为、视觉决定、聚焦验证和未解决冲突。视觉决定应附亮暗模式截图或可复现的浏览器状态；交互决定应覆盖对应的状态变化及失败路径。

## 下次官方更新流程

1. 以 `autoflow-v0.3.0` 标签为起点；集成前将后续自定义工作保存为可审查的 Git 状态。文件清单用于定位改动，不能恢复文件内容。
2. 将 `deepseek-harness` 推进到新的官方提交，并记录前后两个官方提交 ID。官方分支不加入 AutoFlow 修改。
3. 按子系统比较这段官方更新，再对照 `main` 的同名文件、[文件清单](autoflow-local-change-manifest.json)和本次样式基线。先处理有状态功能与公开接口，再列出拟覆盖的视觉差异并询问用户。
4. 将功能新增连同消费者和文档集成到 `main`。功能依赖的新增样式一并合入；本地样式保持原样，除非用户已确认具体替换。
5. 对受影响范围进行聚焦类型、构建、交互、双语文档和浏览器检查。失败项明确记录为未解决，已知回归不能标记为集成完成。
6. 集成后更新本文和文件清单；大版本发布时再创建中文版本标签记录。

## 外观设置后续设计

当前通用设置包含亮色/暗色/跟随系统选项和会话正文字号。[外观页方案](autoflow-appearance-proposal.zh.md)及其 [SVG 示意图](assets/autoflow-appearance-concept.svg)展示了独立分区的设计。方案中的颜色预设、字体家族、圆角、密度、侧边栏形式、布局、内容宽度和方向仍属于候选设计；当前主题设置 schema 尚未持久化这些选项。以后对比官方更新时需要保留这一区分。

## 限制

文件清单保留提交前的路径和 Git 状态，用于定位本次改动；完整代码由 `autoflow-v0.3.0` 标签保存。官方更新结论仅对应上面的核对时间和 `master` 分支，不代表后续状态或其他分支与标签。外观设置页尚为设计方案。
